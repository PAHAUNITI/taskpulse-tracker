## 1. Общие принципы и философия архитектуры
* **Separation of Concerns (Разделение ответственности):** Код строго разделен на слои: пользовательский интерфейс (UI/Presentation), сервисная бизнес-логика (Business Logic / Application Layer), доступ к данным (Persistence/Repository) и доменные модели (Domain Core).
* **Immutability First (Приоритет иммутабельности):** Запрещены неявные мутации объектов на месте (in-place mutation). Все модифицирующие операции возвращают новые экземпляры структур данных.
* **Parse, Don't Validate (Строгая типизация контрактов):** Все входные данные валидируются на границе системы (API controllers/DTO) перед передачей во внутренние сервисы.
* **Single Source of Truth (SSOT):** Доменные правила, перечисления ролей (`UserRole`) и статусов (`TaskStatus`) зафиксированы в едином модуле `src/domain/contracts.py`.

## 2. Правила именования сущностей (Naming Conventions)

В проекте приняты стандартные инженерные соглашения (PEP 8 / Clean Code):

| Элемент кода | Соглашение | Пример в проекте | Пояснение |
| :--- | :--- | :--- | :--- |
| **Классы и Enums** | `PascalCase` | `AuthService`, `TaskStatus`, `WorklogEntry` | Существительные или именные словосочетания |
| **Функции и методы** | `snake_case` | `authenticate_user()`, `transition_status()` | Глаголы или глагольные фразы |
| **Переменные и атрибуты** | `snake_case` | `user_id`, `issue_key`, `remaining_minutes` | Понятные, самодокументируемые имена |
| **Константы** | `UPPER_SNAKE_CASE` | `MAX_WIP_LIMIT`, `VALID_STATUS_TRANSITIONS` | Неизменяемые глобальные значения |
| **Приватные методы** | `_leading_underscore` | `_hash_password()`, `_verify_token()` | Внутренние вспомогательные операции |
| **Файлы и модули** | `snake_case.py` | `auth_service.py`, `task_validation.py` | Отражают доменную принадлежность |
| **Интерфейсы / DTO** | `PascalCase` | `CreateTaskRequest`, `AuthResult` | Контракты обмена данными |

### Антипаттерны именования (ЗАПРЕЩЕНО):
* Однобуквенные переменные вне коротких счетчиков циклов: `t`, `u`, `x`, `data2` ❌.
* Транслитерация: `zadacha`, `polzovatel` ❌.
* Неинформативные суффиксы: `task_object`, `temp_var`, `do_stuff()` ❌.

## 3. Требования к форматированию кода (Formatting)
* **Длина строки:** не более 100 символов (для читаемости на ноутбуках и в split-view редактора).
* **Отступы:** ровно 4 пробела для Python (табуляция запрещена).
* **Пустые строки:**
  * 2 пустые строки между определениями классов и функций верхнего уровня;
  * 1 пустая строка между методами внутри класса;
  * 1 пустая строка внутри функций для разделения логических блоков (Arrange-Act-Assert).
* **Импорты:** группируются в начале файла в порядке:
  1. Стандартная библиотека Python (`os`, `sys`, `datetime`, `dataclasses`);
  2. Внешние библиотеки (`pytest`, `docx`);
  3. Локальные модули проекта (`from src.domain.contracts import ...`).

## 4. Правила организации файлов и функций (Modularity Limits)
В соответствии со стандартом Everything Claude Code (ECC):
* **Лимит размера файла:** типичный модуль — 150–300 строк. Жесткий лимит — **не более 800 строк на файл**.
* **Лимит размера функции:** компактные функции, выполняющие одну атомарную задачу (Single Level of Abstraction Principle, SLAP) — **не более 50 строк на функцию**.
* **Глубина вложенности (Nesting):** не более 2–3 уровней `if/for`. При превышении — обязательный рефакторинг с ранними возвратами (Guard Clauses / Early Return).

```python
# ✅ ПРАВИЛЬНО: Early Return, плоская структура
def calculate_remaining(estimated: int, spent: int) -> int:
    if estimated <= 0:
        return 0
    if spent >= estimated:
        return 0
    return estimated - spent

# ❌ НЕПРАВИЛЬНО: Лестница вложенности
def calculate_remaining_bad(estimated, spent):
    if estimated > 0:
        if spent < estimated:
            res = estimated - spent
        else:
            res = 0
    else:
        res = 0
    return res
```

## 5. Обработка ошибок (Error Handling)
* **Запрет на глушение исключений (No Silent Fail):** конструкции `except: pass` категорически запрещены.
* **Иерархия доменных исключений:** проект использует специализированные типизированные классы ошибок:
  * `DomainError` — базовый класс ошибок предметной области;
  * `ValidationError` — некорректный формат входных данных;
  * `AuthenticationError` — неверный логин/пароль или истекшая сессия;
  * `PermissionDeniedError` — нарушение ролевого доступа RBAC;
  * `WipLimitExceededError` — превышение допустимого числа задач в колонке;
  * `InvalidStatusTransitionError` — попытка недопустимой смены статуса.
* **Информативные сообщения:** каждое исключение обязано содержать причину сбоя и контекст (например, ключ задачи или имя пользователя).

## 6. Требования к документированию и комментариям
* **Docstrings (Google Style):** каждый публичный модуль, класс и функция документируются многострочными строками документации с описанием аргументов (`Args`), возвращаемого значения (`Returns`) и возможных исключений (`Raises`).
* **Самодокументируемый код > комментарии-очевидности:** не допускаются комментарии вида `# инкрементируем i`. Комментарии пишутся только для объяснения неочевидных бизнес-правил и математических формул расчета.

---

## 7. Требования к информационной безопасности (DevSecOps)
* **Хранение паролей:** пароли никогда не сохраняются в открытом виде. Используются алгоритмы формирования ключа на основе соли (PBKDF2-HMAC-SHA256 с $100\,000$ итерациями или Argon2id).
* **Секреты и токены:** запрещен хардкод паролей и API-ключей в исходном коде. Все конфиденциальные параметры выносятся в `.env` и загружаются через модуль `config/settings.py`.
* **Защита Git:** в файл `.gitignore` включены все маски секретов (`.env*`, `*.pem`, `*.key`, `*.sqlite3`).

## 8. Стандарты работы с Git (Conventional Commits)
Сообщения коммитов формируются строго по международному формату:
```text
<type>(<scope>): <краткое описание в повелительном наклонении>
```
* `feat`: новая функциональность или модуль;
* `fix`: исправление бага или регрессии;
* `docs`: обновление документации, диаграмм, отчетов;
* `test`: добавление или рефакторинг unit-тестов;
* `refactor`: улучшение структуры кода без изменения внешнего поведения;
* `chore`: служебные изменения (обновление `.gitignore`, конфигов).
